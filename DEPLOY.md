# Environment Deployment

**Version:** 1.0
**Status:** Normative for Phase 3 of this repository
**Layer:** 3 of 3 — see [README.md](README.md)

Treats an application environment as a deployable artifact rather than a hand-configured
server.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted
as described in RFC 2119.

## Scope

This document defines the environment bundle format and the operations that deploy,
run, and destroy an environment built from it.

It does not define the core, its configuration keys, or its database schema.
Those belong to the application release the operator supplies, and this layer reads
them rather than reproducing them. Where that boundary matters it is stated
explicitly below, because crossing it is the main way this layer can break a
working server.

---

# Architecture

One authentication service, several independent application databases.

```
                        identity
                    (shared, one)
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
     Environment A           Environment B           Environment C
        │                 │                 │
     application-server           application-server           application-server
        │                 │                 │
   primary_a           primary_b           primary_c
   analytics_a       analytics_b       analytics_c
```

`identity` owns accounts and is shared. Each environment owns its own primary and
analytics databases and its own `application-server` process. Environments share nothing that can
carry content between them.

---

# Environment Components

A deployed environment consists of:

| Component | Owner | Notes |
| --------- | ----- | ----- |
| `application-server` process | this layer | One container per environment. |
| `application.conf` | this layer | Generated by overriding a template. See [Configuration](#configuration). |
| Primary database | this layer | Provisioned, then populated from the bundle. |
| Analytics database | this layer | Provisioned empty from the core's own schema. |
| `forge_environment` row | this layer | Registers the environment with `identity`. See [Registration](#registration). |
| `identity` database and process | the operator | Shared; this layer writes one row and never provisions it. |
| Application assets | the operator | Mounted read-only, shared by every environment. |
| Application binaries and image | the operator | Consumed as released. |

# Environment Bundle

A bundle is a directory describing one environment. It carries content by reference to
packages, or as a single primary dump, or both.

```
extended-environment/
├── manifest.yaml        required
├── README.md            optional
├── primary.sql            optional, see spec.content
├── packages/            optional, local package directories
│   └── customer-profiles/
└── assets/
    └── icon.png
```

```yaml
apiVersion: environment.v1
kind: Environment

metadata:
  name: extended
  displayName: Extended
  description: Application with community extensions
  author: Jon

spec:
  core: example-app

  content:
    baseDump: primary.sql
    packages:
      - name: customer-profiles
        version: "=1.2.0"
      - name: extension-framework
        version: ">=2.1.0 <3.0.0"

  environment:
    id: 2
```

| Field | Type | Required | Notes |
| ----- | ---- | -------- | ----- |
| `apiVersion` | string | yes | `environment.v1`. |
| `kind` | string | yes | `Environment`. |
| `metadata.name` | string | yes | `[a-z0-9][a-z0-9-]{0,31}`. Used to derive database names, container names, and the local deployment directory. |
| `metadata.displayName` | string | yes | Shown in the client's environment list. |
| `metadata.description` | string | no | Free text. |
| `metadata.author` | string | no | Free text, presentation only. |
| `spec.core` | string | yes | Opaque core identifier, matched for exact equality the same way as `spec.targets.core` in [SQL.md](SQL.md). |
| `spec.content.baseDump` | string | no | A path inside the bundle holding a primary dump applied before any package. |
| `spec.content.packages` | array | no | Packages to install into the primary database, in the order listed, after `baseDump`. Constraint grammar as [SQL.md](SQL.md). |
| `spec.environment.id` | integer | yes | The environment's identifier, unique across the shared `identity`. Written to both the config and the `forge_environment` row. |

Rules:

- At least one of `spec.content.baseDump` and `spec.content.packages` MUST be
  present. An environment with no content is not deployable.
- Unknown fields MUST be rejected (`E_BUNDLE_INVALID`), for the same reason as
  in [SQL.md](SQL.md).
- `spec.content.packages` entries resolve against the bundle's own `packages/`
  directory first, then against configured catalogs.

# Derived Names

Every name a deployment creates is derived from `metadata.name`, so an environment can
be identified and cleaned up without a lookup table.

| Thing | Pattern | Example for `extended` |
| ----- | ------- | ---------------------- |
| Primary database | `primary_<name>` | `primary_extended` |
| Analytics database | `analytics_<name>` | `analytics_extended` |
| Container | `application-server-<name>` | `application-server-extended` |
| Deployment directory | `<state-root>/environments/<name>` | `~/.local/share/forge/environments/extended` |
| Primary server port | allocated, see below | `8085` |

Port allocation:

- The operator configures a base application-server port, defaulting to `8085`.
- An environment is assigned the lowest free port at or above the base, recorded in its
  deployment state, and reused on every subsequent start.
- The tool MUST verify the port is free before starting and MUST fail rather
  than reassigning a recorded port (`E_PORT_UNAVAILABLE`). Silently moving a
  port breaks clients that were told where to connect.
- `identity`'s own port is the operator's and is never allocated here.

Underscores appear in database names and hyphens in container names because
MySQL identifiers and container names have different conventions; the tool MUST
NOT normalise one into the other beyond this mapping.

# Configuration

`application.conf` is **generated by overriding a template**, never written from
scratch.

The template is the `application.conf.dist` shipped with the operator's core build,
supplied by configuration. The tool copies it and replaces the value of a fixed,
small set of keys:

| Key | Value |
| --- | ----- |
| `EnvironmentId` | `spec.environment.id` |
| `IdentityConnectionString` | connection to the shared `identity` database |
| `PrimaryConnectionString` | connection to `primary_<name>` |
| `AnalyticsConnectionString` | connection to `analytics_<name>` |
| `DataDirectory` | the read-only application-asset mount point inside the container |
| `ServerPort` | the allocated port |

Rules:

- The tool MUST override only these keys and MUST preserve every other line of
  the template, comments included.
- The tool MUST fail if a key it intends to override is absent from the template
  (`E_CONFIG_KEY_MISSING`). An absent key means the template is not the file
  this layer thinks it is, and appending the key would produce a config the core
  may read differently.
- The `*ConnectionString` values are semicolon-separated
  `host;port;user;password;database`. The tool MUST parse the template's
  existing value and fail if it does not have five semicolon-separated fields
  (`E_CONFIG_FORMAT_UNEXPECTED`), rather than writing a format the core may not
  accept.
- The tool MUST NOT invent, add, reorder, or reformat configuration keys. There
  are hundreds of them, their defaults are the core's, and the only ones this
  layer knows the correct value for are the six above.
- Generated configs contain database credentials. The tool MUST write them with
  owner-only permissions and MUST NOT log their contents.

# Registration

An environment becomes visible to clients through a row in the shared `identity`
database's `forge_environment` table.

Rules:

- The tool MUST read `forge_environment`'s actual column set from
  `information_schema.columns` before writing.
- The tool MUST populate the environment's name, address, port, and identifier.
- The name written is `metadata.displayName`; this is what the client shows in
  its environment list.
- The address written is the operator's configured advertised address — the host
  or IP a application client can reach, which is not necessarily the host the tool
  connects to. The tool MUST take it from configuration and MUST NOT derive it
  from a local interface, a container address, or the database host. Getting this
  wrong produces an environment that appears in the list and cannot be joined.
- The port written is the environment's allocated application-server port.
- The tool MUST fail with `E_REGISTRY_SCHEMA_UNEXPECTED` when a column it needs
  is absent, or when a column it does not recognise is `NOT NULL` without a
  default. It MUST NOT guess a value for an unknown required column, and MUST
  NOT alter the table.
- Registration is idempotent per `spec.environment.id`: deploying the same environment twice
  updates the row rather than inserting a second one.
- Deleting an environment deletes its row.

This is the one place this layer writes into a database it does not own, and the
schema varies between cores and between revisions of the same core. Reading the
schema and refusing surprises is the whole safety mechanism; assuming a column
list would corrupt the operator's account service.

# Operations

```
forge environment deploy <bundle>     provision, populate, configure, register, start
forge environment start   <name>
forge environment stop    <name>
forge environment backup  <name>
forge environment delete  <name>
forge environment list
```

## Deploy

1. Read and validate the bundle. Check `spec.core` against the configured core
   (`E_TARGET_MISMATCH`).
2. Refuse if an environment of this `metadata.name` is already deployed, or if
   `spec.environment.id` is taken by a different environment
   (`E_ENVIRONMENT_EXISTS`, `E_ENVIRONMENT_ID_TAKEN`).
3. Resolve every package in `spec.content.packages` and compute the full install
   plan before writing anything. An unresolvable package stops the deployment
   here.
4. Create `primary_<name>` and `analytics_<name>`.
5. Apply the core's own analytics-database schema to `analytics_<name>`, from the
   operator-supplied path. The tool MUST NOT generate this schema.
6. Apply `spec.content.baseDump` to `primary_<name>` if present.
7. Install packages into `primary_<name>` in order, using the Layer 2
   semantics in [SQL.md](SQL.md) unchanged, including its tracking tables.
8. Generate `application.conf`. See [Configuration](#configuration).
9. Write the `forge_environment` row. See [Registration](#registration).
10. Start the container.
11. Record deployment state.

Failure before step 4 leaves nothing behind. Failure at or after step 4 leaves a
partial deployment recorded in state as `failed`, and the tool MUST report which
step failed and MUST NOT roll back automatically — the databases may hold content
the operator wants to inspect. `forge environment delete` is the explicit cleanup.

## Start And Stop

Start and stop the environment's container. Both MUST be idempotent, and MUST fail
rather than deploying anything if the environment is not deployed
(`E_ENVIRONMENT_NOT_DEPLOYED`).

Stopping an environment does not remove its `forge_environment` row. A stopped environment that still
advertises itself is the core's behaviour to handle, not something this layer
papers over by editing the row on every stop.

## Backup

Dump `primary_<name>` and `analytics_<name>` and the generated `application.conf` into a
timestamped directory under the environment's deployment directory.

The backup MUST include the output of `forge package list` for the primary
database, so a restored primary can be matched against the packages that built it.

## Delete

1. Stop the container.
2. Delete the `forge_environment` row.
3. Drop `primary_<name>` and `analytics_<name>`.
4. Remove the deployment directory.

Rules:

- Delete MUST require explicit confirmation naming the environment, and MUST refuse a
  `--force` that skips it. This drops databases.
- Delete MUST NOT touch the shared `identity` database beyond the single row, and
  MUST NOT touch application assets.

## List

Report each deployed environment's name, environment id, state, port, primary and analytics
database names, and container status.

# Deployment State

Each environment's deployment directory holds the state this layer owns:

```
<state-root>/environments/extended/
├── state.json          name, environment id, port, state, timestamps, bundle hash
├── application.conf        generated
├── compose.yaml        generated
└── backups/
    └── 2026-09-26T14-02-11Z/
```

`state` is one of `deploying`, `running`, `stopped`, `failed`.

The bundle hash is computed the same way as a package hash in
[SQL.md](SQL.md), over the bundle directory, so a redeploy can tell whether the
bundle changed.

The database is not the source of truth for deployment state, and `state.json`
is not the source of truth for what is installed in a primary database — the
tracking tables from [SQL.md](SQL.md) are. The two are kept separate so a lost
state file does not make a primary's contents unknowable.

# Containers

Containers are an implementation detail of this layer. The package and catalog
layers have no knowledge of them.

Each environment runs one `application-server` container. Containers differ only in:

- generated configuration
- database names
- environment identifier
- published port

Every container shares:

- the operator-supplied core image
- the operator-supplied application assets, mounted **read-only**

Rules:

- The tool generates a `compose.yaml` per environment and drives `docker compose`.
  It MUST NOT talk to the Docker API directly, so that a deployment stays
  inspectable and reproducible by hand.
- Application assets MUST be mounted read-only. They are shared and identical
  across environments; a writable mount lets one environment corrupt every other.
- The tool MUST NOT build images. The core image is the operator's.

---

# Environment Isolation

Each environment owns its own primary and analytics databases.

| Benefit | Because |
| ------- | ------- |
| No package conflicts between environments | Package name uniqueness is per database. |
| Deterministic upgrades | An environment's tracking tables describe only that environment. |
| Independent backups | Nothing is shared to restore around. |
| Safe experimentation | Deleting an environment cannot affect another. |
| Multiple simultaneous application configurations | standard, restricted, internal, extended, seasonal, experimental — all at once. |

The shared surface is exactly two things: the `identity` database, written one row
at a time, and the read-only application assets. Everything else is per environment.

# Error Conditions

| Code | Meaning |
| ---- | ------- |
| `E_BUNDLE_INVALID` | Missing, unparseable, wrong `apiVersion`, failed validation, or an unknown field. |
| `E_TARGET_MISMATCH` | `spec.core` does not equal the configured core. |
| `E_ENVIRONMENT_EXISTS` | An environment of this name is already deployed. |
| `E_ENVIRONMENT_ID_TAKEN` | `spec.environment.id` belongs to a different environment. |
| `E_ENVIRONMENT_NOT_DEPLOYED` | The operation requires a deployed environment and found none. |
| `E_PORT_UNAVAILABLE` | The allocated or recorded port is in use. |
| `E_CONFIG_KEY_MISSING` | A key to be overridden is absent from the template. |
| `E_CONFIG_FORMAT_UNEXPECTED` | A template value did not have the expected shape. |
| `E_REGISTRY_SCHEMA_UNEXPECTED` | `forge_environment` lacks a needed column, or requires one this layer cannot supply. |
| `E_ANALYTICS_SCHEMA_MISSING` | The operator-supplied analytics-database schema was not found. |
| `E_CONTAINER_FAILED` | `docker compose` returned a failure. |
| `E_DEPLOY_INTERRUPTED` | State was found as `deploying` from an earlier run. |

# Future Evolution

The architecture allows a public ecosystem of environment distributions: creators
publish environment bundles as catalog artifacts, and operators deploy them with one
command. Nothing in the bundle format changes to allow that — a bundle is bytes
with a digest, and Layer 1 already carries bytes.

The bundle format's `spec.content.packages` is the direction of travel. A bundle
that references packages instead of shipping a `primary.sql` dump is smaller,
upgradeable in place, and auditable package by package, which a dump is not.

# Design Philosophy

This layer standardises deployment around existing application capabilities rather
than modifying them.

Environments become versioned artifacts that can be deployed, upgraded, backed up, and
deleted consistently. The deployment system runs entirely outside the core, so a
core update is adopted by pointing at a new image and a new template.

The recurring rule is that this layer owns what it creates and reads what it does
not. It creates databases, configs, containers, and state, and it may change
those freely. It reads the core's config template, the core's analytics schema,
the `forge_environment` schema, and the application assets — and where it must write into
something it does not own, it inspects first and refuses surprises rather than
adapting to them.
